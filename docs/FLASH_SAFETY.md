# STC32G12K128 烧录安全核验

更新：2026-10-18。结论：**STC32G12K128 独立烧录已通过实机验证**。验证设备为 BSL 7.4.5U、CH340/COM20；测试写入代码区并确认结束响应，未写入 EEPROM 或硬件选项。

本文区分手册事实、主机程序行为与设备实测结果。该验证结论仅适用于已验证的 STC32G12K128 UART 下载路径，不代表所有 STC 型号兼容。

## 1. 存储器布局：已有手册证据

参考《STC32G 系列单片机技术参考手册》，资料更新日期 2022/11/24。本地原文件名 STC32G.pdf，共 1056 个 PDF 页面；不随本仓库分发。已经提取相关完整页面，并对涉及布局、表格的关键页面进行渲染复核。

| 问题 | 手册证据 | 能确定什么 |
|---|---|---|
| 128 KiB Flash 地址 | 印刷页 213，PDF 第 236 页，9.1 | STC32G12K128：FE:0000H～FF:FFFFH；复位入口 FF:0000H |
| 小于 64 KiB 的代码 | 印刷页 105，PDF 第 128 页，5.10 | Large 模式链接到 FF:0000～FF:FFFF |
| 超过 64 KiB 并保留 EEPROM | 同上 | Huge 模式；EEPROM 从 FE:0000 开始；代码必须避开预留区。例如保留 8 KiB 时避开 FE:0000～FE:1FFF |
| 1 KiB EEPROM 地址 | 印刷页 460–461，PDF 第 483–484 页，18.3 | CPU MOV 地址 FE:0000～FE:03FF；IAP 地址 0:0000～0:03FF |
| 硬件选项生效时机 | 印刷页 131，PDF 第 154 页，5.14 | 部分配置需重新上电；“下次下载时擦除 EEPROM”是后续下载相关选项 |

**不能推断**：CPU/IAP 地址并不等于 ISP 报文字段。不能据此直接删除 HEX 高位、互换 FE/FF 两区，或声称擦除仅影响 HEX 有数据的位置。IAP 的 512 字节扇区规则也不能直接当作 ISP 擦除范围。

该手册相关章节说明了配置界面和生效时机，但没有给出可用于本项目的完整 STC32 ISP 选项包字节/位编码。这是有限章节核查，不是“整本手册绝无协议”的断言。

## 2. 现有主机后端的可重复风险

审计对象：本仓库保留的 MIT stcgal 1.10，来源提交 `fdf5fdd60515a260bb303dcf7b251c2b2671f91c`。

离线测试：`test/test_programming_contract.py`。其串口构造函数被显式禁止，读写函数替换为内存队列，只使用模拟数据。

### 2.1 超过 64 KiB 的失败不是安全预检查

`Stc8dProtocol` 继承的 `program_flash()` 使用 `struct.pack('>H', offset)` 编码偏移，块大小为 64 字节。模拟 65,537 字节输入时，前 1,024 个块已经交给模拟发送函数，在偏移 65,536 处才抛出异常，没有发送结束包。

这是**主机侧先分发、后报错**的复现，不是实机烧坏记录。未来实现必须在任何擦除/写入前检查完整地址范围，不能依赖写入过程中才发现越界。支持 128 KiB 还需要确认 STC32 的跨区传输机制。

### 2.2 固定应答不等于独立读回校验

当前主机代码接受 `02 54` 的块应答及 `07 54` 的结束应答。模拟设备没有保存任何固件、没有返回任何读回数据，写入函数仍返回成功。

可确定：当前主机流程没有独立读取 Flash 再逐字节比较。不能确定：芯片是否在生成应答前进行了内部校验、内部校验覆盖范围或是否存在其他校验命令。传输帧校验和、命令应答、Flash 校验、程序功能验证是不同层次。

### 2.3 小 HEX 不等于小范围擦除

向 `erase_flash()` 提供 64 字节或 64,000 字节的代码大小，在同一 `flash_size=65536` 条件下生成相同擦除报文；该报文不编码这两个具体长度。超过传入 `flash_size` 后切换另一标志。

可确定：不能把输入长度直接展示为实际擦除字节数。芯片端真实擦除范围、当前 EEPROM 配置对其影响，仍需官方协议或独立验证。

### 2.4 保留五个字节不等于保留全部选项

`build_options()` 将五个 MSR 字节放入一个 40 字节块，同时写入频率、校准值、分频数及若干常量。省略用户选项参数不代表不会写配置；上游命令行正常烧录流程会调用 `program_options()`。

此前已观察到通用 STC8 解码的复位脚结果与用户提供的官方工具显示冲突。不能依据一次状态采集直接反转某个位，更不能把分区字段零解释为“没有 EEPROM”。

## 3. 证据来源与边界

- [stcgal STC15/STC8/STC8D 协议实现](https://github.com/grigorig/stcgal/blob/fdf5fdd60515a260bb303dcf7b251c2b2671f91c/stcgal/protocols.py)：`handshake`、`erase_flash`、`program_flash`、`build_options`、`program_options`。
- [stcgal 烧录调用流程](https://github.com/grigorig/stcgal/blob/fdf5fdd60515a260bb303dcf7b251c2b2671f91c/stcgal/frontend.py)：`program_mcu`。
- [相关型号 STC32G8K64 的复位脚问题 #114](https://github.com/grigorig/stcgal/issues/114)：相关风险提示，不是当前型号的相同缺陷证明；核查时无后续评论提供解决方案。
- 另审阅 `Jihao2048/stc-newisp-cli` 的 UART 实现及验证说明（提交 `4971163cf74af94b150c34f67a5bbd098004961f`）：同样不足以独立确认本板的配置保留与 Flash 校验语义。没有复制该 GPL 项目的实现。
- 当前源码核查不等于分析了官方 STC-ISP 二进制；没有新的官方实现分析结果。此前原生分析环境不可用，本轮没有安装分析工具或重复尝试同一不可用能力。

## 4. 开放烧录前的证据门槛

1. 明确 STC32G12K128 / BSL 7.4.5U 的选项读写编码，至少覆盖复位脚、EEPROM 分区和下载时擦除行为。
2. 确定 CPU 地址到 ISP 地址的映射、跨 64 KiB 机制以及擦除范围；在发送前完成越界检查。
3. 明确可用验证机制及其强度：真实读回或有规格依据的芯片端校验。不得把固定 ACK 包装成读回校验。
4. 首次实机写入必须使用用户明确同意覆盖的测试程序/测试板，并事先说明 EEPROM 风险及恢复方案。

下一项需要的新证据是官方 ISP 协议说明，或对用户提供的 STC-ISP 的聚焦离线实现分析；重复 RES 识别无法补齐这些字段。配置独立原生分析环境需另行确认。当前不提供隐藏烧录开关、试烧命令或自动配置修改。
